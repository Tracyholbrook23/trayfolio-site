# Client Dashboard / CMS Architecture Proposal
### For valtiermedia-site, designed to become a reusable Trayfolio system

Status: proposal only. Nothing in the codebase has been touched. This is meant to be read, argued with, and revised before any code gets written.

## 1. What's actually in the repo right now

Here's what I found inspecting valtiermedia-site directly.

**Framework and routing**
Next.js 16.3.1 (App Router), React 19.2.8, TypeScript strict mode, Tailwind v4. Routing is the standard `app/` file-based router: `/`, `/about`, `/contact`, `/faq`, `/services`, `/work`, plus four case-study pages under `/work/*`. No `output: "export"` in `next.config.ts`, so this is a normal hybrid SSR/SSG deploy on Vercel, not a static export. That matters a lot for what follows: Vercel's on-demand caching and revalidation are fully available to us.

**Components**
Organized into `components/sections/` (page-level blocks like the hero and work showcase), `components/ui/` (the design-system pieces: buttons, galleries, the contact form), and `components/hooks/`. No component library like shadcn is installed, everything is hand-built Tailwind. This is good news for the "clients never touch layout" requirement: there's no drag-and-drop-friendly component abstraction here to accidentally expose, content and presentation are already cleanly separate at the code level.

**Content storage today**
Entirely hardcoded in TypeScript:
- `lib/work-items.ts`: a single `shoots` array typed as `Shoot[]`, driving the whole `/work` portfolio and its filter pills.
- `lib/service-items.tsx`: the five service cards (title, description, image, icon) shared by the homepage preview and `/services`.
- Everything else (hero copy, About page text, FAQ entries, contact info) is inline JSX/string literals directly inside the page files.

Worth calling out: `lib/work-items.ts` already has a comment anticipating this exact project ("this is also the seam for the planned admin upload feature... this static array gets replaced by a fetch from wherever that feature stores them"). You (or a past session) already scoped this seam correctly.

**Database / backend**
None. No API routes, no middleware, no server-side data layer of any kind.

**Authentication**
None.

**Images**
388 MB under `public/gallery`, committed straight to git, referenced by string path, rendered with plain `<img>` tags (zero `next/image` usage anywhere in the codebase). No resizing, no format negotiation, no lazy-loading pipeline. Every image is baked into the deployment at build time.

**Forms / APIs**
One form (`components/ui/contact-form.tsx`), and it posts directly from the browser to Web3Forms' hosted API with a public access key. There is no server-side code involved in it at all today, not even an API route.

**Deployment**
GitHub repo `Tracyholbrook23/Valtiermedia-site` → Vercel project `valtiermedia-site` (org `team_LibWdR11TBOThhYyNxZfaNsW`). Every push triggers a full rebuild and redeploy. That's fine for a hardcoded marketing site; it's the wrong model for "Dom fixes a typo in his hours" (see section 8).

**Environment variables**
Two: `VERCEL_OIDC_TOKEN` (Vercel-managed) and `NEXT_PUBLIC_WEB3FORMS_ACCESS_KEY` (intentionally public). No secrets infrastructure exists yet, but you've already established a clean pattern on other client sites (Stripe, Square, Resend keys as Vercel env vars, never `NEXT_PUBLIC_`), so there's nothing new to invent there.

**Security posture**
Actually more mature than the average marketing site: `next.config.ts` already ships a real CSP, `X-Frame-Options: DENY`, `nosniff`, a trimmed referrer policy, and disabled camera/mic/geolocation. Whoever wrote it (you) left detailed comments explaining every choice. This will need a few additions once there's a login and file uploads (section 12), but it's a solid foundation, not a rewrite.

**One more thing worth knowing**: this repo has an `AGENTS.md` note (auto-generated by `next dev`) warning that Next.js 16 has behavior that may differ from older training data and pointing at `node_modules/next/dist/docs/` for the current docs. Before writing real code against Draft Mode, revalidation, or middleware APIs, that's worth a quick read rather than assuming an older Next.js version's conventions still apply exactly.

## 2. What would need to change

- **Page components** (`app/page.tsx`, `app/about/page.tsx`, `app/services/page.tsx`, `app/contact/page.tsx`, `app/faq/page.tsx`) stop importing hardcoded strings/arrays and instead call a `getContent()`-style server function for the fields you've marked editable. Everything *not* marked editable stays exactly as it is: hardcoded, developer-controlled, untouched.
- `lib/work-items.ts` and `lib/service-items.tsx` split into two layers: a developer-owned **shape/schema** (categories that exist, which fields are editable, validation rules) and client-owned **values** (the actual text/prices/images), the latter now living in a database instead of a TS file.
- Images referenced by editable fields move out of `/public` into blob storage (section 9). Portfolio/gallery images that stay fully developer-curated (ordering, case-study layout, category taxonomy) can reasonably stay as-is for now, per your own instinct not to move every string into a database. More on where I'd draw that line in section 10.
- `next.config.ts`'s CSP needs `img-src` extended to the blob storage domain, and that's essentially it. No relaxation of `script-src` is needed.
- New additions, none of which touch existing pages: `/client/login`, `/client/dashboard/*`, a handful of API routes or Server Actions, `middleware.ts` for route protection, and a database.

## 3. Authentication architecture

**Recommendation: a small, hand-rolled auth layer**, using `iron-session` for encrypted, signed httpOnly cookies, `bcryptjs` for password hashing, a custom login Server Action, and your own rate limiting.

**Why not a bigger library (Auth.js/NextAuth), and why not a managed vendor (Clerk, Supabase Auth)?**

The actual requirement here is narrow: email + password, three roles, one business per deployment. That's not what those tools are optimized for:

- **Auth.js (NextAuth)** is the "safe default" choice and I considered recommending it, but most of its surface area (OAuth provider abstraction, magic links, multiple adapter types) is dead weight for this use case, and it's a moving target across major versions. It's a reasonable fallback if you'd rather not own the login flow yourself, but for a package you intend to drop into every future client repo, less dependency surface means fewer version conflicts and less to audit each time.
- **Managed auth vendors (Clerk, Supabase Auth, etc.)** charge per project or per MAU, which multiplies badly across a growing roster of client sites, and they'd force each client's login to live on a third party's infrastructure just for a few dozen users. That's real cost and real complexity for something bcrypt + a signed cookie handles fine at this scale. It also matches a pattern you've already chosen elsewhere (Stripe and Square integrations built as plain `fetch` calls instead of pulling in their SDKs, specifically to keep the dependency footprint small).

`bcryptjs` specifically (not `bcrypt`) because it's pure JavaScript with no native binary to compile, which sidesteps the exact class of Linux-vs-Mac native-binary problem you've already hit with `lightningcss` on this project via the device bridge.

**Shape of it:**
- `users` table: `id`, `email`, `password_hash`, `role` (`OWNER` / `CLIENT_ADMIN` / `CLIENT_EDITOR`), `name`, `disabled_at`.
- Login Server Action verifies the password, then sets an encrypted `iron-session` cookie (httpOnly, `Secure`, `SameSite=lax`) containing `userId` and `role`.
- `middleware.ts` gates everything under `/client/*`, redirecting to `/client/login` if there's no valid session.
- **The role in the cookie is a hint, not a trust boundary.** Every Server Action or route handler that mutates data re-reads the user's role from the database before acting, never trusts the cookie's claim alone for anything destructive (user management, publish, rollback). This is the actual answer to "a client must never be able to manipulate a request and access another client's content": because every client's data lives in that client's own database (section 5), there is no cross-tenant query to construct in the first place. The isolation is physical, not just a `WHERE tenant_id = ?` clause someone could forget.
- Login attempts rate-limited (Upstash's free-tier rate limiter, which you're already using on Shawnie's site, is a fine fit here too) to blunt brute-forcing.
- Roles are designed in from day one even though you'll likely only create one `CLIENT_ADMIN` account (Dom) at first. Adding a `CLIENT_EDITOR` later is just a new row with a different role value, no schema change.

## 4. Database / content storage architecture

**Recommendation: Neon Postgres (serverless, scales to zero) via Vercel's Neon integration, with Drizzle ORM.**

**Why Postgres at all, instead of something simpler?** You need relations (versions belong to a site's history, users belong to roles, media belongs to fields), structured querying, and transactional writes (publish has to be all-or-nothing). A key-value store like the Upstash Redis you used for Shawnie's donation counter is great for a single counter; it's the wrong tool for a CMS with drafts, versions, and an audit trail.

**Why Neon specifically, and why Drizzle over Prisma:**
- Neon has a genuinely useful free tier, scales to zero when idle (so a low-traffic client site costs nothing when nobody's editing), and integrates into Vercel's dashboard in a couple of clicks, same deployment story you already use everywhere else.
- Drizzle is a thin, lightweight query builder rather than a heavy code-gen ORM. It works cleanly with Neon's HTTP driver in serverless functions, has a much smaller runtime footprint than Prisma, and its schema is just TypeScript, which makes it easy to package and reuse across client repos (section 10). Prisma's generated client and binary engine are exactly the kind of "extra infrastructure per project" this system is trying to avoid.
- Alternative considered: **Supabase**, which bundles Postgres + Auth + Storage in one product. Tempting for "fewer moving parts," but its built-in auth model doesn't map cleanly onto an `OWNER` role that needs to reach across many *separate* client databases, and it pulls you toward its specific SDKs everywhere. Composable pieces (Neon + your own auth + Vercel Blob) stay swappable if any one of them stops being the right fit later.

**Schema, one database per client site (see section 6 for why per-site rather than shared):**

```
users
  id, email, password_hash, role, name, disabled_at, created_at

content_values          -- what's LIVE on the site right now
  id, section_key, field_key, value (jsonb), updated_at, updated_by
  unique(section_key, field_key)

content_drafts          -- the client's in-progress, unpublished edits
  id, section_key, field_key, value (jsonb), updated_at, updated_by
  unique(section_key, field_key)

content_versions        -- append-only publish history
  id, version_number, snapshot (jsonb), published_by, published_at, note

media_assets
  id, blob_url, blob_key, alt_text, width, height,
  focal_x, focal_y, mime_type, size_bytes, uploaded_by, created_at

audit_log               -- append-only, never editable via the app
  id, actor_user_id, action, entity, entity_id, diff (jsonb), created_at
```

`content_values` and `content_drafts` are deliberately narrow (one row per field) rather than one giant JSON blob per page. That keeps validation, audit diffing, and partial updates simple, while still letting a single field hold a JSON array for repeatable content (FAQs, team members, testimonials) without inventing a join table for every list. This is the "don't overengineer" middle ground: normalized enough to audit and diff cleanly, not so normalized that adding a new field type means a migration.

## 5. The editable-content schema (the reusability core)

This is the part your `editableFields` sketch was pointing at, and it's the single most important piece for making this reusable. The dashboard should have **zero knowledge** of what fields exist for any given site. It just renders whatever a schema file describes.

```ts
// content.schema.ts, lives in each client's own repo, developer-authored
type FieldType =
  | "text" | "textarea" | "email" | "phone" | "url"
  | "price" | "number" | "select" | "image" | "list";

interface FieldDef {
  key: string;
  label: string;
  type: FieldType;
  required?: boolean;
  maxLength?: number;
  minLength?: number;
  min?: number;
  max?: number;
  pattern?: string;          // e.g. for phone formats
  options?: string[];        // for "select"
  itemSchema?: FieldDef[];   // for "list", e.g. one FAQ = { question, answer }
  helpText?: string;         // shown under the field in the dashboard
  imageSpec?: {              // for "image"
    aspectRatio: string;     // "16:9", "1:1", etc.
    maxSizeMB: number;
    recommendedWidth: number;
  };
}

interface SectionDef {
  key: string;
  label: string;             // shown in the dashboard nav, e.g. "Home Page"
  fields: FieldDef[];
}

export const contentSchema: SectionDef[] = [
  {
    key: "home",
    label: "Home Page",
    fields: [
      { key: "heroHeading", label: "Hero Heading", type: "text", required: true, maxLength: 60 },
      { key: "heroSubheading", label: "Hero Description", type: "textarea", maxLength: 160 },
      { key: "heroImage", label: "Hero Image", type: "image", imageSpec: { aspectRatio: "16:9", maxSizeMB: 8, recommendedWidth: 1920 } },
    ],
  },
  {
    key: "faq",
    label: "FAQs",
    fields: [
      {
        key: "items", label: "Questions", type: "list",
        itemSchema: [
          { key: "question", label: "Question", type: "text", maxLength: 100, required: true },
          { key: "answer", label: "Answer", type: "textarea", maxLength: 500, required: true },
        ],
      },
    ],
  },
];
```

The dashboard, the validation logic, and the form renderer are all generic code that walks this array. Adding a new editable field on this site, or standing up the whole dashboard on a brand new client site, becomes "write a schema file," not "build a new form." Validation rules (`maxLength`, `pattern`, required-ness) are enforced identically on the client (instant feedback) and the server (the actual security boundary, never trust the browser).

This directly answers your "if a heading is designed for ~60 characters, don't let a client paste a 500-character paragraph" requirement: it's a `maxLength` in one place, applied everywhere.

## 6. Tenant / client isolation

**Recommendation: one deployment, one database, per client. Not a shared multi-tenant database with a `tenant_id` column.**

You're already doing this: every client gets their own GitHub repo and Vercel project. I'd keep that structure rather than collapsing everyone into one shared app, and here's the trade-off explicitly:

**Physical isolation (recommended):** Dom's data lives in Dom's own Neon database, in Dom's own Vercel project. There is no query path from Dom's site into another client's data, because there is no other client's data anywhere it could reach. This is strictly stronger than row-level isolation in a shared database, where a single missing `WHERE tenant_id = ?` clause becomes a cross-client data leak. It also means a bug, an outage, or a security incident on one client's site can't cascade to another's.

**Shared multi-tenant platform (the alternative):** one app, one database, every client's content tagged by `tenant_id`. This is the architecture you'd want if you were running an actual SaaS product with hundreds of tenants, because operating N separate databases doesn't scale past a certain point. At your current and near-future scale (a handful of client sites, solo-maintained), it trades away isolation and adds real complexity (tenant-scoped queries everywhere, one outage affects everyone, one compromised row-level-security policy affects everyone) for an operational win you don't need yet.

Given your own stated priority order (security and "clients unable to break their website" above reusability and performance), physical isolation is the right call today. If you ever cross into "dozens of clients and I want one dashboard to rule them all," the schema and dashboard code from section 5 transfers directly into a multi-tenant version, it's the same forms and the same validation, just reading `tenant_id`-scoped rows instead of a whole database. Nothing here is wasted if you outgrow it.

The `OWNER` role doesn't need special cross-database plumbing to work today: since you (Tracy) are the one creating every client's `OWNER` account, you just log into `dom-site.com/client/login` with an `OWNER` account the same way Dom logs in with a `CLIENT_ADMIN` account. Full cross-site visibility (see all clients from one screen) is a thin layer on top, described in section 11, not something the core architecture needs to bake in now.

## 7. Draft → Preview → Publish

This maps almost exactly onto a Next.js feature built for exactly this problem: **Draft Mode**.

- **Save Draft**: writes to `content_drafts`. Nothing on the live site changes. This can happen as often as the client wants, no validation-blocking beyond "is this a well-formed value," full validation is enforced on Publish.
- **Preview**: a "Preview" button in the dashboard enables Draft Mode (a signed, httpOnly cookie Next.js manages for you) and opens the *actual* site in a new tab. The exact same page components render, but your `getContent()` function checks for that cookie and reads from `content_drafts` instead of `content_values` when it's present. This is the direct answer to "I would like the preview to use the actual website/components rather than trying to recreate the website inside the dashboard": it's not a simulation, it's the live site, temporarily reading unpublished data, visible only to someone with that signed cookie. Nobody else can see draft content, and it isn't cached publicly.
- **Publish**: a single transaction: copy every `content_drafts` row into `content_values`, insert one snapshot row into `content_versions`, write an `audit_log` entry, then call `revalidateTag()` for the affected sections (see section 8). Draft Mode is exited automatically once there's nothing left to preview, or the client can toggle back to live view manually.

No separate "preview environment" or second deployment is needed. This is one of the bigger wins of building on Next.js's App Router rather than a static export.

## 8. Publishing without a full redeploy

Because this stays a normal Next.js deployment (not static export), you get on-demand cache invalidation for free: **`revalidateTag`**.

Every content read gets tagged, e.g.:

```ts
const heroHeading = await getContentValue("home", "heroHeading", { tags: ["content:home"] });
```

When Dom hits Publish, the Server Action that writes to `content_values` calls `revalidateTag("content:home")` right after the database write completes. Vercel's Data Cache and the page's rendered output for anything depending on that tag get invalidated immediately, the next request (often within the same second) regenerates the page with the new content. No git push, no build, no redeploy. This is the direct technical answer to "I do not necessarily want a full application redeployment every time someone changes a sentence."

Practically: each `SectionDef` in the schema (home, services, about, etc.) gets its own cache tag, so publishing a change to the About page doesn't invalidate or regenerate the Home page's cache.

One caveat worth flagging honestly: Next.js 16's exact caching/revalidation APIs are worth re-verifying against that repo's own bundled docs (see the `AGENTS.md` note in section 1) before implementation, since the caching model has been an area of real change across recent Next.js versions and I'd rather you get the current, correct API than one I'm recalling from older training data.

## 9. Image storage and processing

**Recommendation: Vercel Blob for storage, `sharp` for server-side processing, `next/image` for delivery.**

Today's model (commit every image to `/public`, ship it with the build) fundamentally cannot support client uploads: every new photo would need a git commit and a redeploy, which is exactly what this whole project exists to avoid. Client-uploaded images need to live outside the git repo, in object storage.

**Why Vercel Blob over Cloudinary/S3+CloudFront/imgix:** it's a couple of lines of setup inside the same Vercel account you're already paying for, no new vendor relationship per client site, and paired with `sharp` (already the industry-standard image library, pure enough to run in a Vercel serverless function without native-binary headaches beyond what Vercel already handles for it) it covers everything you listed: resizing, format conversion, compression. Cloudinary and imgix offer fancier on-the-fly transform URLs, but that's a subscription per project you don't need when `sharp` + `next/image` already does the job at this scale.

**The upload pipeline:**
1. Client picks a file. Before it ever leaves the browser: validate extension *and* re-check the actual file signature isn't spoofed, enforce the size cap from that field's `imageSpec`.
2. Client-side crop/reposition UI (a simple library like `react-easy-crop`, or hand-rolled since the interaction is just "drag to reposition, pinch/scroll to zoom within a fixed-aspect-ratio frame") lets the client fit their photo to the required aspect ratio *before* upload, with a live preview. This is the direct answer to "if a hero image is supposed to be 16:9, uploading a portrait phone photo shouldn't destroy the hero section": the client sees and confirms the crop before it's ever saved, they can't submit an uncropped portrait photo into a 16:9 slot.
3. Upload goes to a server action, never straight to Blob from the browser unvalidated. Server re-validates size/type (never trust client-side checks alone), strips EXIF metadata, re-encodes through `sharp` (this also neutralizes most image-based exploit tricks, since the output is a freshly generated file, not the visitor's original bytes), generates the field's required aspect ratio, and stores both the processed image and a small thumbnail.
4. The image row also stores a `focal_x`/`focal_y` percentage (from the crop step) rather than baking the crop in destructively, so `object-position` can do the final framing responsively. This is cheap, reversible, and avoids ever losing the original framing choice.
5. Delivery goes through `next/image` pointed at the Blob URL (added to `remotePatterns` in `next.config.ts`), which gets you responsive `srcset` generation, lazy loading, and modern-format negotiation (WebP/AVIF) automatically, on every image on the site, not just the new client-editable ones. Worth doing as part of this project regardless of the CMS, since the site currently ships zero image optimization at all.

## 10. Content model: what's actually worth exposing

You explicitly said not to blindly move every string into a database, and I'd hold that line. Rough split, based on what I saw in the codebase:

**Good candidates for client editing** (matches your own list almost exactly): hero heading/subheading, About/business description, service names + descriptions + prices, hours, contact info (phone/email/address), FAQs, testimonials, CTA button text, hero image, a bounded "team member" list (name/title/photo/bio), and a capped-count gallery upload slot per category.

**Should stay developer-controlled**, at least for now: the *portfolio/case-study system* (`lib/work-items.ts` and the four dedicated case-study pages). That's not really "content," it's information architecture: which categories exist, how many photos justify a category existing at all (you have a documented rule about this already), whether a shoot gets a dedicated case-study layout or the default lightbox. Handing a client the ability to create new categories or restructure that would be handing them layout decisions in disguise. If you want Dom to eventually add new shoots himself, I'd scope that as a narrower feature later ("upload photos into an existing category") rather than folding it into this first phase.

Also developer-controlled: page structure/routes, nav items, SEO metadata structure (a "meta description" field could become editable later without much extra work, but I wouldn't include it in the first schema), and obviously everything about layout, animation, and styling.

## 11. Admin / Trayfolio layer

Nothing about the design above blocks any of your eventual admin wishlist, but I'd deliberately *not* build a separate Trayfolio-wide admin app in phase one; it's the one part of this request that's genuinely a different, standalone project. Here's why it's not hard to bolt on later:

- **See all client websites / recent edits / published versions**: each site already has an `audit_log` and `content_versions` table. A tiny `/api/admin/summary` route (protected by a per-site `TRAYFOLIO_ADMIN_API_KEY` env var, not a user login) can expose "last edit," "current version," "editing enabled." A future Trayfolio admin app just polls that endpoint across however many client sites you have.
- **Disable client editing**: a single boolean on the site (or even just disabling the `CLIENT_ADMIN`/`CLIENT_EDITOR` accounts) already covers this, no new architecture needed.
- **Restore content**: already the rollback feature from section 7, just exposed to `OWNER` only.
- **Impersonate a client's dashboard for support**: since `OWNER` already has full access on every individual client site, "impersonation" in phase one is just you logging into that client's own `/client/login` with your `OWNER` account. True impersonation-without-a-separate-login only becomes meaningfully different once there's a central Trayfolio app aggregating multiple sites, which is a phase-4+ concern.

Building this now would mean standing up and paying for a service that has no users yet. Worth doing once you have several client dashboards running and the busywork of checking each one individually actually starts to hurt.

## 12. Security concerns, and how each is addressed

| Concern | How it's handled |
|---|---|
| Cross-client data access | Physical DB-per-client isolation (section 6); no shared query surface exists |
| Privilege escalation (editor doing admin things) | Role re-checked server-side from the database on every mutation, not trusted from the session cookie |
| Stored XSS / script injection | All client text fields render through React's default escaping; no field is ever put through `dangerouslySetInnerHTML`, so there's no "rich HTML" field type in the first version at all |
| Malicious file uploads | Server-side re-validation of file signature (not just extension), full re-encode through `sharp` (also strips embedded payloads), randomized storage keys (no user-controlled filenames), enforced size caps before processing |
| Brute-force login | Rate limiting on the login route (Upstash), account lockout/backoff |
| Session hijacking | httpOnly, `Secure`, `SameSite` cookies via `iron-session`; short-lived sessions |
| CSRF | Server Actions carry Next.js's built-in origin verification; if any plain API routes are used instead, explicit same-origin checks are added |
| Secrets exposure | DB URL, Blob token, session secret, admin API key all as Vercel encrypted env vars, never `NEXT_PUBLIC_` |
| Oversized/malformed input crashing a function | Every field's `maxLength`/size caps enforced server-side before any processing happens, not just in the UI |
| "Something changed and I don't know why" | Append-only `audit_log`, never exposed to deletion via the app itself |
| CSP gaps once uploads exist | `img-src` extended to the Blob domain; no relaxation of `script-src` needed |

## 14. Reusability: the actual package boundary

**Recommendation: a private shared package, `@trayfolio/cms-core`, installed from a private GitHub repo** (`npm install github:Tracyholbrook23/trayfolio-cms#v1.0.0`), not a paid private npm registry, not a monorepo across all client sites (those live in separate repos today and I wouldn't force them into one just for this).

What lives in the shared package:
- The dashboard UI: the schema-driven form renderer, the nav generated from `SectionDef[]`, the image crop/upload widget, the version-history/rollback UI.
- Field-type validators (shared between client-side and server-side checks).
- The image processing pipeline (`sharp` steps, Blob upload helper).
- The auth helpers (session creation/verification, password hashing, the login form).
- The Drizzle schema factory for the six tables in section 4.
- Thin, reusable Server Action implementations (`saveDraft`, `publish`, `rollback`, `uploadImage`) that each site's own route files import and call.

What stays in each client's own repo:
- `content.schema.ts`: what's editable on *this* site.
- Its own `page.tsx` files, updated to call `getContent()` instead of importing static data.
- Its own env vars (`DATABASE_URL`, `BLOB_READ_WRITE_TOKEN`, session secret).
- A handful of one-line route files that just re-export the package's handlers.

Standing this up on a second client site later should genuinely mean: write a schema file, add three env vars, update the page components to read from `getContent()`, done. That's the reusability bar this is designed to hit.

One deliberate sequencing note: I'd build this whole thing end-to-end on valtiermedia-site first, and only extract it into the shared package once it's proven on one real site (phase 6 below). Abstracting before you have a single working implementation tends to produce the wrong abstraction; better to let the real constraints of Dom's actual content shape the package.
